# 知伴低风险自动写入与回滚设计

> 状态：2026-08-05 产品裁断已通过，已实施并完成自动化与 SM-W7023 真机验收。
> 基线：`e118bcf2c924267f23e7a401dfaaf9190da39caf`。
> 目标：让显而易见、仅影响本机内部数据、可完整撤销的写入自动执行；任何条件不满足时自动降级为逐次确认。

## 一、实施前代码核验结论

1. `RuntimeToolRisk` 当前只有 `READ_ONLY / WRITE_CONFIRMATION_REQUIRED / HIGH_RISK` 三档；`ActionPolicy` 仅让只读工具自动执行。
2. `ProviderExecutionEngine` 的主调用循环和工具观察循环都直接按 `risk == READ_ONLY` 分支。新增风险档后必须同时改这两个最终调用点，不能只改枚举。
3. `CapabilityRouter` 当前只有 `executeReadOnly` 和确认执行路径，没有“可逆自动写”专用入口。
4. `change_log` 已有 `inversePayloadJson`、`undoState`、幂等键和 90 天撤销窗口；但聊天中的撤销被 `runtimeRunId` 绑定，不能直接服务于 Runtime 之外的自动采集。
5. `ChangeUndoCoordinator` 当前只实现联系人候选、关系候选、联系人资料和日历的撤销。CRM Writer 虽生成部分 inverse payload，但所有 CRM ChangeLog 都标为 `UNAVAILABLE`，当前不能声称可撤销。
6. `AgentDataRepository.recordAutoInteractionEvidence()` 会在联系人匹配置信度 `>= 0.99` 时直接写 `INTERACTION_SUMMARY` Fact；该写入没有 ChangeLog、没有可见回执、没有通用撤销入口。
7. 当前互动摘要按“联系人 + 平台 + 日期”覆盖聚合。若直接把旧 Fact 原文塞进 inverse payload，会违反 ChangeLog“不保存联系人明文 PII”的约束。因此该路径需要调整为可单条撤销的数据模型，不能简单补一条 ChangeLog。

## 二、四档 ActionPolicy

```text
READ_ONLY
  → 自动读取，不产生持久化变更

REVERSIBLE_AUTO_WRITE
  → 同时满足 inverse、ChangeLog、可见撤销三项才自动执行
  → 任一条件不满足，降级为 WRITE_CONFIRMATION_REQUIRED

WRITE_CONFIRMATION_REQUIRED
  → 普通逐次确认

HIGH_RISK
  → 强确认；不可逆或可能产生外部影响
```

### 2.1 决策输入

`ActionPolicy` 不只看静态风险枚举，还要接收经过 Router/Binding 验证的能力证明：

```kotlin
data class ReversibleWriteReadiness(
    val inverseSupported: Boolean,
    val atomicChangeLogSupported: Boolean,
    val visibleUndoSupported: Boolean,
)
```

判定规则：

- `REVERSIBLE_AUTO_WRITE + readiness 全 true` → `AutoExecute(REVERSIBLE_WRITE)`。
- `REVERSIBLE_AUTO_WRITE + 任一 false` → `RequireConfirmation`，使用固定原因码，不包含异常或用户数据。
- 用户已经逐次确认时，`REVERSIBLE_AUTO_WRITE` 允许走普通确认执行路径，作为自动资格不足时的安全兜底。
- `WRITE_CONFIRMATION_REQUIRED/HIGH_RISK` 不得因为 Binding 自报“可撤销”而升级为自动执行。

固定降级原因码：

- `auto_write:inverse_unavailable`
- `auto_write:audit_unavailable`
- `auto_write:undo_surface_unavailable`
- `auto_write:evidence_insufficient`
- `auto_write:target_changed`
- `auto_write:policy_rejected`

## 三、结构性三重门

不能让每个调用点自己判断“三条件”。采用三个注册表和一个专用 Binding 接口形成结构保证：

1. **Inverse 注册**：`ReversibleAutoWriteBinding` 必须实现事务内的自动执行和确认执行；普通 `RuntimeToolBinding` 不能进入自动写路径。
2. **Undo 注册**：工具名必须存在于 `ChangeUndoCoordinator` 的显式 handler registry。
3. **Presentation 注册**：工具名必须存在于 `AutoWritePresentationRegistry`，定义展示标题、目标解析方式和纠正入口。

App 组装 `CapabilityRouter` 时注入 inverse/undo/presentation 三个注册集合；运行时逐个 Binding 校验。缺任一注册，Router 只能请求确认。

专用自动写入口不得复用 `executeReadOnly()`：

```kotlin
sealed interface ToolDisposition {
    data object ReadOnly : ToolDisposition
    data object ReversibleAutoWrite : ToolDisposition
    data class ConfirmationRequired(val strong: Boolean, val reasonCode: String) : ToolDisposition
}
```

`ProviderExecutionEngine` 的主循环和观察循环统一调用 Router 获取 disposition，禁止再直接比较风险枚举。

## 四、自动执行的原子流程

每次自动写必须在同一个 Room 事务内完成：

1. 重新读取目标与证据，做资格判断，避免预检到执行之间状态变化。
2. 在变更前生成最小 inverse command；不得把完整通知、手机号、邮箱等原文放入 ChangeLog。
3. 执行业务变更。
4. 写 `change_log(undoState = AVAILABLE)`。
5. 写 `auto_write_receipts` 可见回执。
6. Runtime 工具写入 ToolAudit、幂等执行记录和 RuntimeEvent。
7. 提交事务后把安全结果交给模型观察循环。

任何一步失败，整个事务回滚。资格在事务内不再满足时抛固定的 `AutoWriteDowngradeException`，Provider 执行器转入正常确认卡片，不允许留下半条数据。

### 4.1 数据库调整

数据库版本计划由 30 升至 31：

- `change_log.runtimeRunId` 改为可空，使通知采集等非 Runtime 写入不必伪造 run。
- `change_log` 新增 `originType`：`RUNTIME_TOOL / SYSTEM_PERCEPTION / USER_CORRECTION`。
- 新增 `auto_write_receipts`，它只是 UI 投影，不替代 ChangeLog 审计：

```text
changeId             PK/FK -> change_log
subjectContactId     nullable, FK SET_NULL
sourceType           固定枚举，不存原始消息
sourceRefDigest      只存摘要
confidence           nullable
presentationType     固定枚举
correctionRoute      固定枚举
reviewState          UNREVIEWED / SEEN / CORRECTED
createdAtEpochMs
```

回执内容通过 `targetDomain + targetId + presentationType` 从当前本地实体投影；目标撤销后只显示固定的“已撤销”摘要，不在回执表复制敏感原文。

### 4.2 撤销并发与防误伤

- 聊天内撤销继续校验 `runtimeRunId`。
- “知伴自动整理”入口只能撤销存在可见回执、`undoState=AVAILABLE` 的自动变更。
- Undo handler 必须比较 `afterDigest` 与目标当前状态。用户后来手动修改过目标时，不覆盖新内容，而是返回“内容已变化，请纠正”。
- 业务 inverse 成功后才能 `markUndone`；两者处于同一事务。
- 撤销窗口沿用现有 90 天；365 天后删除终态审计记录。

## 五、首批风险清单

### 5.1 进入 `REVERSIBLE_AUTO_WRITE`

| 操作 | 自动资格 | inverse | 纠正方式 |
|---|---|---|---|
| 通知互动摘要（内部 action，不暴露给模型） | 唯一联系人精确匹配；置信度 `>=0.99`；来源不是服务号/系统通知；有稳定 source key | 删除本次生成的 Fact | 选择正确联系人；原自动写撤销后写一条用户纠正记录 |
| `contact.tag.add`（新增 ToolSpec） | 已有真实联系人；单一非空标签；不含电话/邮箱；证据可追溯；置信度 `>=0.99` | 删除本次新增的精确标签；若标签原本存在则幂等 no-op | 打开联系人标签编辑 |
| `crm.lead.createCandidate` | 联系人已存在且唯一；不自动建联系人；sourceRef/evidence 完整；置信度 `>=0.99`；只进入 `CANDIDATE` 候选池 | 删除该 Agent 候选线索 | 候选池中转正或忽略 |
| `crm.activity.append` | 机会、联系人均明确；活动来自一条稳定的已采集证据；不允许纯模型臆测 | 删除本次新增活动 | 打开机会详情活动编辑 |
| `crm.nextAction.create` | 明确机会；只建 CRM 内部 PENDING 动作；不创建日程、不发提醒；时间若存在必须来自明确证据 | 删除本次新增动作 | 打开机会详情动作编辑 |

实施后 Provider 可见 ToolSpec 从 26 增为 27（新增 `contact.tag.add`）；内部互动摘要 action 不计入 Provider ToolSpec 数量。手册必须同步更新实际数量。

### 5.2 保持 `WRITE_CONFIRMATION_REQUIRED`

- `calendar.schedule.create/update/delete`：当前写的是正式日程，并可能产生提醒，不是“候选”。本轮没有任何现有日历写操作符合自动条件。
- `memory.remember/delete`：改变 Agent 长期认知或删除用户记忆。
- `contact.createCandidate`、`contact.profile.proposeUpdate`：涉及身份、电话、邮箱、公司、职位等核心档案。
- `relationship.createCandidate`：改变核心关系网络语义。
- `crm.opportunity.create/update/changeStage`：影响机会主体、金额、关键联系人、预测和阶段。
- `crm.nextAction.update/complete`：修改或完成用户已有工作安排。
- 所有删除操作，即使技术上可恢复，也至少逐次确认。
- 远端 MCP 写操作和 `communication.message.compose`。

消息中的日程只有在日期、时间、动作均明确，联系人唯一匹配，且本地与系统日历均无冲突时，才可自动写入本机日程；写入必须同时生成可见回执和完整撤销记录。星期表达、群聊、联系人不唯一、冲突或系统日历不可读取时一律降级确认。同步外部日历仍需确认。

### 5.3 永远不进入自动写

- 发送消息、邮件、报价、拨号、发布内容、付款等对外行为。
- 调起分享/发送界面的行为至少 `WRITE_CONFIRMATION_REQUIRED`；未来若支持直接发送则为 `HIGH_RISK`。
- 永久删除、密钥操作、权限变更、远端副作用不明确的 MCP 操作。

## 六、互动摘要从黑箱迁入治理体系

当前“联系人 + 平台 + 日期”聚合 Fact 不适合逐条撤销。首批实现调整为：

- 每个稳定通知 source key 对应一条幂等 `INTERACTION_SUMMARY` 证据 Fact。
- inverse 只保存 `deleteFactId`，不保存通知原文。
- 关系页展示时按联系人/日期聚合，检索层可继续限流和聚合，持久层不覆盖旧证据。
- 自动写入 Fact、ChangeLog 和回执在一个事务中完成。
- `recordAutoInteractionEvidence()` 仍是采集链最终写入点，但 Fact、ChangeLog 和回执由同一个外层 Room 事务包裹；审计与回执统一走 `insertVisibleAutoWrite()`，不再出现只写 Fact 的黑箱分支。
- 自动资格不足时保留为通知候选，让用户确认联系人，不静默丢弃。

存量已有的聚合 Fact 不伪造 ChangeLog；迁移时保留并标为“历史自动整理，不支持单条撤销”，按原 90 天 TTL 自然到期。不能按内容猜测拆分。

## 七、用户可见入口

### 7.1 关系页

- 联系人搜索/关系图上方增加紧凑的“知伴自动整理”卡片，仅在存在 90 天内可查看、可撤销记录时出现。
- 显示最新 1–3 条：来源、联系人、时间、置信度、写入了什么。
- 每条提供“撤销”和“纠正”；不弹阻断式弹窗，不在进入关系页时自动展开。

### 7.2 我的页

- 增加常驻“知伴自动整理”入口与未读数量。
- 打开独立设置子页，按“可处理 / 已撤销”展示最近记录。
- 仅显示脱敏来源摘要；完整消息仍留在对应联系人/CRM 的本地详情里。

### 7.3 纠正语义

- 互动摘要：联系人选择器中重新归属；“撤销原自动写 + 写入用户纠正记录”同事务完成。
- 联系人标签：进入该联系人标签编辑。
- CRM：进入对应机会、活动或下一步动作编辑。
- 用户主动点击并保存纠正即构成明确确认，不再弹第二次确认。

## 九、测试与验收

### 9.1 必须新增的单元测试

- readiness 三项全有 → 自动写。
- inverse / audit / visible undo 任一缺失 → 固定原因码并降级确认。
- `WRITE_CONFIRMATION_REQUIRED/HIGH_RISK` 永不被 readiness 提升为自动。
- Provider 主循环和观察循环都能执行 reversible auto write。
- 自动资格在事务内失效 → 0 业务变更、0 ChangeLog、0 回执，随后进入确认。
- 对外工具即使错误注册 readiness 也不能自动。

### 9.2 数据库与设备测试

- 自动写、ChangeLog、回执同事务提交；注入任一步失败时三者均不落库。
- 同一 source/idempotency 重放只产生一条业务记录和一条 ChangeLog。
- 自动互动摘要可撤销，Fact 从检索和联系人详情消失，ChangeLog 变 `UNDONE`。
- 目标被用户修改后撤销不会覆盖新内容。
- 纠正联系人后原变更已撤销，新记录关联正确联系人且有审计。
- CRM 线索/活动/下一步动作逐项验证创建、撤销、重放幂等和降级确认。
- UI 能看到来源、联系人、时间、置信度，并从关系页和我的页完成撤销。

### 9.3 最终门槛

- `./gradlew check`
- 使用仓库外签名执行 `./gradlew assembleRelease`
- SM-W7023 全量 `connectedDebugAndroidTest`
- 真机手工走一遍：采集一条构造通知 → 自动整理可见 → 撤销 → 重新触发 → 纠正联系人。
- 真机确认对外消息仍停在用户最终确认/目标应用发送页，绝不自动发送。

## 十、已落实的产品裁断

本轮按以下范围实施：

1. 自动写包含：互动摘要、联系人标签新增、高置信且无冲突的本机消息日程、CRM 线索候选、CRM 活动追加、CRM 下一步动作创建。
2. 普通或有歧义的日程、联系人核心资料、关系边、机会主体/金额/阶段、已有动作的修改与完成继续逐次确认。
3. “知伴自动整理”采用关系页条件卡片 + 我的页常驻入口；不在进入页面时自动弹窗。
4. 自动写撤销窗口沿用 90 天；目标已被用户修改时不强行回滚，改为引导纠正。

补充裁断：自动线索一律写成 `status=CANDIDATE`，不进入正式线索、机会、胜率或预测；用户确认“转正”后才进入正式线索列表。首次产生自动写时只显示一次轻提示，此后保持安静。

CRM 工作台以独立候选池展示 `CANDIDATE`；转正必须再次确认。转正后进入“正式线索”区并计入推进概览的线索数量，忽略则通过 ChangeLog 撤销并从候选池消失。
