# 知伴代码规范（Agent 可执行版）

> 提炼自 Clean Code / Pragmatic Programmer / Code Complete / DDD / GoF，适配 Kotlin + Compose + Room + Hilt。
> 每条规则机器可校验，模糊表述已转为"必须/禁止"。

---

## 一、命名规范

**R1. 名字必须见名知意——禁止 tmp/data/info/manage/process 这类无信息量词。**
- ✅ `suspend fun importConfirmedSystemContacts()`
- ❌ `fun processData(d: String)`

**R2. 布尔变量/函数必须以 is/has/can/should 开头。**
- ✅ `val hasIdentity: Boolean`
- ❌ `val identity: Boolean`

**R3. 常量必须全大写下划线、放 companion object。**
- ✅ `companion object { const val NOTIFICATION_GAP_THRESHOLD_MS = 30 * 60_000L }`
- ❌ `private val threshold = 1800000`

---

## 二、函数规范

**R4. 单函数必须 ≤80 有效行（detekt LongMethod 已配）。超长必须拆——按"做了一件事"的粒度。**
- ✅ `fun normalize(sourceType, factType, value)` 只做归一化
- ❌ 一个 `execute()` 同时做检索组装 + 网络预检 + 流式 + 确认文案

**R5. 函数参数必须 ≤5 个。超过的必须封装为参数对象。**
- ✅ `fun save(planEnvelope: PlanEnvelope)` — 一个对象封装多字段
- ❌ `fun create(id, name, phone, email, company, title, tag, note, source, confidence)`

**R6. 函数必须只做一件事——能用一句话描述它做什么。如果描述里有"和"，就必须拆。**
- ✅ "把通知候选确认并写入 Fact" — 一件事
- ❌ "读取通知、匹配联系人、生成 Fact、发通知给用户" — 四件事

**R7. 禁止用异常做正常控制流。异常只用于真正的异常情况。**
- ✅ `return Result.failure(ProviderFailure("TIMEOUT", retryable = true))`
- ❌ `throw NormalFlowSignal()` 来跳出循环

---

## 三、架构规范

**R8. 每个类必须只有一个变更理由（SRP）。构造参数 ≤8。**
- ✅ `ContactAgentDataRepository` 只管联系人 CRUD
- ❌ `AgentDataRepository` 同时管通知 + 联系人 + 日历 + CRM + 记忆

**R9. 依赖方向必须单向——UI → 业务 → 数据，禁止反向。**
- ✅ agent 子模块不 import `com.zhiban.rebuild.ui`
- ❌ `data/agent/AgentDataRepository` 里 `import com.zhiban.rebuild.ui.chat.PreferencesManager`

**R10. 多表写必须在同一事务内（Room withTransaction）。跨表操作禁止各自独立事务。**
- ✅ `database.withTransaction { saveUserContact(); confirmNotificationCandidate() }`
- ❌ 先调 `saveUserContact()`（自开事务），再调 `confirm()`（又开一个），中间崩溃留半成品

**R11. DRY——相同逻辑出现 ≥2 次必须抽公共函数。禁止复制粘贴。**
- ✅ `parseToolArgs(argumentsJson, allowedKeys)` 各 ToolBinding 共用
- ❌ 16 个 ToolBinding 各自 `runCatching { Json.parseToJsonElement(...) }`

**R12. 正交性——改一个功能不应该需要动不相关的文件。**
- ✅ 加新工具只改 ToolBinding + Catalog
- ❌ 加新工具需要改 ProviderExecutionEngine 构造函数

---

## 四、测试规范

**R13. 每个 public 函数必须有至少一个测试。测试名必须描述被测行为。**
- ✅ `fun multiplePhoneNumbersOnSameContactAreAllMatchedAsSelf()`
- ❌ `fun test1()`

**R14. 测试必须 Arrange-Act-Assert 三段式。禁止依赖测试执行顺序。**
- ✅ 每个测试自建 fixture、自验证、自清理
- ❌ test2 依赖 test1 往数据库塞的数据

**R15. suspend 链路的错误处理必须用 runSuspendCatching 不用 runCatching。**
- ✅ `runSuspendCatching { suspendFunc() }` — 取消正确传播
- ❌ `runCatching { suspendFunc() }` — 吞掉 CancellationException

**R16. 测试/生产文件比必须 ≥0.4（用尺子量）。**
- ✅ 145 测试文件 / 240 生产文件 = 0.60
- ❌ 50 测试 / 300 生产 = 0.17

---

## 五、边界与错误处理

**R17. 用户输入和外部数据（通知/模型输出/MCP 返回）必须在入口校验。禁止盲目信任。**
- ✅ `require(name.isNotBlank()) { "INVALID_TOOL_ARGUMENTS" }`
- ❌ 直接 `Json.parseToJsonElement(modelOutput)` 不做大小/结构/字段校验

**R18. 敏感数据（手机号/邮箱/地址/消息内容）出境前必须经过 OutboundDataPolicy。禁止裸发。**
- ✅ `PolicyEnforcingProviderAdapter` 包在生产 Provider 最外层
- ❌ 直接 `OkHttpClient.newCall(request).execute()` 绕过 Gate

**R19. 资源（Cursor/Stream/WebSocket/Bitmap/AudioRecord）必须在 finally 或 use 块释放。**
- ✅ `contentResolver.query(...).use { cursor -> ... }`
- ❌ `val cursor = contentResolver.query(...)` 无 use/finally

**R20. 禁止吞异常——catch 块必须至少记录降级原因码。空 catch 块禁止。**
- ✅ `catch (_: Throwable) { degradation.add("retrieval:failure") }`
- ❌ `catch (_: Exception) {}` 静默吞掉

**R21. 禁止硬编码密钥/Token/密码。凭据必须经 KeystoreCredentialVault。**
- ✅ `vault.withCredential(ref) { key -> ... }`
- ❌ `val apiKey = "sk-xxxxxxxx"`
